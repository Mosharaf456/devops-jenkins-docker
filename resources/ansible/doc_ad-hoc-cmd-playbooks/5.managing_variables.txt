Managing variables
ansible variable is similar to using variables like any programming language.
That can be used to store values which can be reused throughout files in an entire ansible project.

Variables provie a convenient wat to mange dynamic values for a given environment in your ansible project.

Some example of values that variable might contain include.

1. User to create 
2. Package to install 
3. Service restart 
4. Files to remove

Naming variables: 
consist of string, must start letter, can only contain alphanumeric, underscores.

################********variable scope*******:
Global scope: Variable set from command line or Ansible configuration.
Play scope: Variables set in the play and related structures.
Host scope: Vaiables set on host groups and individual hosts by the inventory, fact gathering or registered tasks.

Variables in playbooks
When writing playbooks, administrators can use their own variables and call them in a task.

For example, a variable web_package can be defined with a value of apache2 and called by the apt module in order to 
install the apache2 package.

---
- name: Install apache and start the servcie 
  hosts: dev 
  vars:
    web_pkg: apache2
    firewall_pkg: ufw 
    web_service: apache2 
    python_pkg: python-httplib2 
    rule: apache2 
  tasks: 
    - name: Install the required packages 
      apt:
        - "{{ web_pkg }}"
        - "{{ firewall_pkg }}"  
        - "{{ python_pkg }}"
      state: present

ansible.builtin.set_fact
Use Case:
ansible.builtin.set_fact is used to define variables dynamically during playbook execution. These variables persist for the duration of the playbook run and can be used in later tasks.

Dynamic Variable Assignment: Useful when you need to compute and store a value during runtime.
Conditional Execution: Helps store computed values that can be referenced in subsequent conditional tasks.
Loop Optimization: Store intermediate results from loops to avoid recomputation.
Caching for Later Use: Facts set using set_fact remain available throughout the playbook execution.

Example Use Case: 
- name: Set a dynamic variable
  ansible.builtin.set_fact:
    app_version: "1.2.3"

- name: Use the dynamically set variable
  debug:
    msg: "The application version is {{ app_version }}"

Accessibility:
Variables set with set_fact are available only for the duration of the playbook run.
They do not persist across playbook runs unless explicitly written to a file or stored in a persistent system (e.g., an Ansible inventory plugin).
Accessible within the same playbook, including in later tasks, conditionals, and loops.
Can be used across roles if included in a playbook, but not automatically available across separate playbook runs.


Key Differences & Use Cases
Use set_fact when:
You need to compute a value during playbook execution (e.g., based on task results).
You want to set a value dynamically inside a loop or condition.
You need to store a value that depends on runtime environment or host facts.

- name: Get OS type
  debug:
    msg: "OS is {{ ansible_os_family }}"

- name: Set package name dynamically
  ansible.builtin.set_fact:
    package_name: "{{ 'httpd' if ansible_os_family == 'RedHat' else 'apache2' }}"

- name: Install web server
  ansible.builtin.apt:
    name: "{{ package_name }}"
    state: present
  when: ansible_os_family == "Debian"


- hosts: all
  vars:
    default_port: 80

  tasks:
    - name: Set a custom port if it's a production environment
      ansible.builtin.set_fact:
        web_port: "{{ 443 if ansible_env['ENV'] == 'production' else default_port }}"

    - name: Print the web port
      debug:
        msg: "Using port {{ web_port }}"


Use vars for static, predefined values.
Use set_fact when values depend on runtime conditions

Ansible facts are variables that are automatically discovered by Ansible from a managed host.
In simple word: Ansible facts are predefined variable.

And with the help of setup module from your ansible server, 
you can retrieve the values of those variables from your managed host at any time.

Facts are pulled by the setup module and contain usefull information stored into variables that administrators can reuse.
Ansible facts can be part of playbooks, in coditions, loops, or any other dynamic statement that depends on a value for administrators 
managed host.

For example : 
A server can be retstarted depending on the current kernal version
Users can be created depending on the host machine.

{{ ansible_hostname }}
{{ ansible_default_ipv4.address }}
{{ ansible_dns.nameservers }}
{{ ansible_kernel }}

What is the scope of a variable defined in a playbook?
Task scope - accessible only within the specific task it,s defined for. 

What is the order of precedence for variables in Ansible?
Host variables> Playbook Variables > Group var > Role defaults 

Which Ansible command-line option allows you to display all the variables defined for a specific host?
> anisble --list-hostvars

Which Ansible module allows you to display facts for a specific host?
> ansible -m setup 

How can you disable facts gathering for a specific playbook?

Set gather_fatc: false in the playbook
